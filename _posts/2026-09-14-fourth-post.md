<h1>解题核心：篡改客户端逻辑突破限制</h1>
客户端环境完全受用户控制，所有客户端校验（HTML 属性、JS 逻辑、隐藏字段）都只是建议而非约束，安全控制必须由服务端强制执行
# 解题过程
- 侦察页面
- 定位限制来源：F12 打开开发者工具，用元素选择器（Ctrl + Shift + C）点击输入框，Elements 面板定位
- 修改属性并提交：双击 maxlength="1"，将值改为 "999"

# 关于前端，客户端和服务端
<p>前端 = 用户能看见、能点的界面部分</p>
- 网页前端技术：HTML、CSS、JavaScript
<p>客户端 = 安装在设备上的程序，是和用户直接交互的整体软件</p>
- 包含前端界面，也包含本地逻辑
<p>服务端 = 放在远程服务器上，负责处理数据的程序</p>
- 前端/客户端只是发请求：“帮我查个数据”；服务端接收请求，处理后返回结果
# 细节原理
`maxlength` 属于浏览器本地执行的约束，和 JS 表单校验、禁用的按钮、隐藏的 `input` 一样，**全部只运行在客户端**。客户端对用户是完全开放的：
- `maxlength`限制长度，F12 可以随意增删改 DOM 属性（此题）
- Burp Suite 可以在请求发出前拦截并修改任意参数（**Burp 改包**：随便输 1 位数字点验证，用 Burp 拦截请求，把答案参数改成正确值再放行）
- `curl` / Python 脚本可以完全无视页面、直接构造 HTTP 请求（**脚本提交**：观察验证请求的参数名，用 Python `requests` 直接 POST 正确答案）
服务端拿到答案后没有做长度或格式的二次校验，”信任”了前端传来的数据，
# 安全概念
前端校验绕过，Web 安全的黄金法则：**前端校验只能用于体验优化（即时提示），真正的防线必须建在服务端**。凡是重要逻辑——长度、格式、权限、价格——服务端都必须重新验证一遍

# 延伸对应攻击场景
- JS禁用提交按钮，删除disabled属性/直接发请求
- 隐藏字段携带价格、折扣，改包修改隐藏字段值
- 前端JS判断用户身份，跳过页面直接调接口
